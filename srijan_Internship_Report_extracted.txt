Abstract  

This internship report presents the design, implementation, and optimization of Retrieval Augmented Generation(RAG) pipeline developed for the AI Receptionist Assistant (ANA) project at the Research Management Cell (RMC) Department of Kantipur City College. The main goal of the project was to implement an accurate, high-performance, and entirely local question-answering interface for college queries without depending on external cloud APIs.

During the internship period from May 13, 2026 to July 8, 2026, I was involved in local model benchmarking, retrieval tuning, and answer generation optimization. The RAG module utilizes FAISS for multi-file vector indexing combined with Sentence-Transformers embeddings, enabling efficient similarity search across college documents. To overcome domain-specific challenges, we implemented keyword-based routing, custom lexicon normalization for college acronyms (e.g. BCA-IT, BBA, BBS), and a hybrid answering strategy that combines retrieved context with generative responses. The generation module integrates Qwen3-1.7B served via an Ollama/Lemonade backend, producing natural, context-grounded answers directly on local hardware, supported by a keyword-based fallback interface for low-confidence queries.  

The completed RAG pipeline was integrated into the local application server, achieving low-latency retrieval and response generation suitable for real-time interaction. The results demonstrate that local open-source RAG systems are highly suitable for interactive reception systems, preserving student privacy and avoiding recurring cloud API costs.

1.2 Problem Statement:  

Retrieval and generation in local interactive reception desks face several challenges:  

Inconsistent document formatting, mixed file types, and unstructured institutional content often result in poor chunking and irrelevant retrieval in typical RAG systems.  

General-purpose embedding models perform poorly with domain acronyms (e.g.  BCA-IT, BBA, BBS) and localized names (e.g. teacher and coordinator names like 

Ravi sir).  

Short or ambiguous queries (e.g., 'fees', 'timing', 'result') are easily misrouted without keyword-based routing, requiring custom matching thresholds.  

Large language model-based answer generation introduces computational latency, making the interactive agent feel sluggish and unresponsive during live conversations.  

Purely retrieval-based answering fails on queries with no direct document match, requiring a hybrid fallback strategy to avoid returning empty or irrelevant responses.  

1.3 Objectives  

The primary objectives of this internship were:  

To develop a local retrieval service using FAISS for multi-file semantic indexing of institutional documents.  

To build a hybrid answering system that combines retrieved context with generative responses using Qwen3 served via Ollama/Lemonade.  

To implement a robust keyword-based fallback mechanism to guarantee relevant responses in case of low-confidence retrieval.  

To customize retrieval and routing logic to prevent mismatched results for course names (BCA-IT) and staff names.  

To filter out low-confidence or irrelevant matches from the retrieved context before generation.  

1.4 Scope and Limitation  

The scope of my work covers the FAISS-based retrieval service, multi-file document indexing, keyword-based query routing, hybrid answer generation, lexicon normalization, and backend API service routes.  

Limitations: The system uses embedding models optimized primarily for English. It does not natively support mixed English-Nepali code-switched queries or highly ambiguous, multiintent questions. It relies on local system hardware (a GPU is preferred for lowlatency generation via Ollama/Lemonade, falling back to CPU when unavailable), and retrieval accuracy depends on the quality and structure of the indexed source documents.

Chapter 3: System Research  

3.1 System Overview   

The RAG module serves as the brain of the AI receptionist. When a user asks a question, the system follows this pipeline:  

  Step 1: User input is received as a text query   

  Step 2: A keyword classifier checks if the query is college-related  

  Step 3: If college-related, the query is embedded and searched across all FAISS indexes   

  Step 4: The most relevant document chunks are retrieved  

  Step 5: Retrieved chunks are passed to the LLM along with the query and chat history  

  Step 6: The LLM generates a natural language response   

  Step 7: If no relevant chunks are found, the LLM answers from general knowledge

3.3 Literature Review  

A review of literature on conversational AI systems shows a clear shift toward local model execution in institutional settings. While cloud-based APIs (such as OpenAI's GPT models or commercial vector database services) offer high accuracy, they suffer from internet latency, recurring monthly costs, and data privacy issues. Grounding a college assistant locally on a single workstation requires lightweight, efficient architectures like FAISS for vector similarity search and compact instruction-tuned language models such as Qwen3 for generation. Modern systems mitigate accuracy limitations in domain-specific settings by using keyword-based routing, custom lexicon normalization, and hybrid retrieval-generation strategies, matching cloud performance locally.  

The quality of retrieval in turn depends heavily on the embedding model used to represent text; Sentence-Transformers, based on the Siamese BERT-network architecture proposed by Reimers and Gurevych (2019), has become a widely adopted standard for producing semantically meaningful sentence embeddings suited to similarity search tasks. Modern systems mitigate accuracy limitations in domain-specific settings by using keyword-based routing, custom lexicon normalization, and hybrid retrieval-generation strategies. This hybrid approach, combining sparse keyword matching with dense semantic retrieval, has been shown in recent literature to outperform either method alone, particularly for short or ambiguous queries common in conversational interfaces, allowing local deployments to closely match the performance of cloud-hosted systems while preserving data privacy and eliminating recurring API costs.

4.2 Implementation Details  

Document Indexing: Each knowledge file (TXT or PDF) is processed separately. Text is extracted, split into 500 character chunks with 50-character overlap, embedded using allMiniLM-L6-v2, and stored in a dedicated FAISS index. This allows precise retrieval from the correct source file.  

Query Routing: A keyword-based classifier first checks if the query contains institution related terms (e.g., KCC, admission, BCA, semester, faculty). If matched, the system searches across all FAISS indexes and selects the one with the lowest distance score. If no relevant chunks are found within the relevance threshold, the query falls back to general knowledge.  

Answer Generation: The retrieved chunks are injected into a structured prompt along with the full chat history, enabling the LLM to generate contextually accurate and conversational responses. Streaming is enabled for real-time token-by-token output. A postprocessing step removes markdown symbols to ensure clean plain-text output.  

Chat History: Every user query and assistant response is stored in a chat history list. This full history is sent with every API call to the LLM, enabling multi-turn conversations where the assistant remembers previous context.

4.5 Tasks / Activities Performed  

The implementation details of the two core services I developed are:  

Retrieval service: The service wraps FAISS for vector similarity search across multiple institutional documents. We configured a multi-file indexing pipeline using Sentence-Transformers embeddings, with each document chunked and tagged by source for traceability. We also designed a keyword routing layer: a query is matched against a domain-specific keyword map first, and falls back to dense vector search when no strong keyword match is found, ensuring acronyms like BCA-IT are routed correctly instead of being lost in generic semantic similarity.  

Answer generation wrapper: The service uses Qwen3-1.7B served through a local Ollama/Lemonade backend. It combines the top retrieved chunks into a context window, constructs a grounded prompt template, and streams the generated response back through the API layer. A confidence threshold on retrieval similarity scores determines whether the system answers directly from retrieved context or falls back 

to a general keyword-based response, preventing irrelevant or hallucinated answers when no matching document exists.
